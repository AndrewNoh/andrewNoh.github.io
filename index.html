복구 가능한 시스템으로 설계합니다.

결제수단별 구현을 하나의 실행 구조로 통합하고, 실패한 거래가 유실되지 않도록 복구 흐름을 설계하며, 승인·반환·여정변경의 금액을 동일한 기준으로 계산해 왔습니다.

Engineering Principles

시스템을 설계할 때 지키는 기준

기술이나 패턴을 먼저 선택하기보다, 데이터가 어긋날 수 있는 지점과 실패 이후의 처리 흐름을 먼저 확인합니다.

01

Failure First

외부 기관과 네트워크는 언제든 실패할 수 있다는 전제에서 시작합니다. 정상 처리뿐 아니라 망취소, 재처리, 데이터 보정까지 하나의 업무 흐름으로 설계합니다.

02

Data Integrity

잘못된 금액이나 상태를 저장한 뒤 보정하는 것보다, 계산 과정과 객체 생성 시점에서 불변식을 검증하여 데이터 오염을 먼저 차단합니다.

03

Explicit Flow

짧고 추상적인 코드보다 업무 처리 순서와 책임이 자연스럽게 읽히는 구조를 중요하게 생각합니다. 팀원이 메인 흐름만 따라가도 시스템을 이해할 수 있어야 합니다.

Architecture Case Studies

설계 판단과 문제 해결 과정을 설명합니다.

결과만 나열하지 않고 문제의 제약, 선택한 구조, 실패 처리와 트레이드오프를 실제 구현 흐름에 맞춰 정리했습니다.

Case 01

Strategy Registry Net Cancel Recovery Batch

결제 수단 라우팅과 실패 복구

결제수단마다 다른 승인·롤백·취소 구현을 호출 서비스가 직접 선택하지 않도록 공통 실행 구조를 만들었습니다. 실패한 망취소와 일반 취소는 유형별로 DB에 적재하여 별도 배치 서버가 다시 처리하도록 구성했습니다.

  • 결제 구현체를 애플리케이션 시작 시 key 기반 Map으로 자동 등록
  • Command와 Detail만 전달하면 Executor가 적절한 구현체의 process 실행
  • 망취소 실패와 일반 취소를 구분하여 취소 배치 대상으로 관리
  • 배치 장애 시 DB 설정으로 즉시 취소 방식 전환 가능

Case 02

Amount Allocation Tax & Fee Domain Normalization

수납·결제 금액 통합 분배 엔진

승인, 반환, 여정변경마다 비교해야 하는 수납정보와 기존 결제정보가 달랐지만, 필요한 정보를 공통 금액 모델로 변환하여 동일한 메서드에서 금액을 분배하도록 설계했습니다.

  • 4~5종류의 요청 및 DB 정보를 공통 금액 모델로 정규화
  • 약 14개 결제수단의 업무 우선순위에 따라 금액 분배
  • 공급가액·부가세·면세금액·수수료를 매핑 행별로 배분
  • 승인 당시 금액을 초과하는 반환을 저장 전에 차단

Case 03

AES / RSA Hypothesis Testing External Integration

복호화 실패 원인 역추적과 공식 가이드 개선

공식 가이드의 암호화 규격으로 승인 결과를 복호화할 수 없는 상황에서, 입력 인코딩·RSA 결과 처리·AES Key 길이·IV를 독립적인 가설로 나누어 실제 적용 규격을 확인했습니다.

  • 복호화 변수 조합을 반복 검증하는 테스트 구조 작성
  • 부분 복호화 결과를 분석해 Key와 IV 문제를 분리
  • 여러 카드사의 실제 승인 데이터로 동일한 결과 검증
  • 분석 내용을 외부 기관에 전달하여 공식 가이드 수정

제한 네트워크 환경의 메시징

대규모 데이터 성능 검증
